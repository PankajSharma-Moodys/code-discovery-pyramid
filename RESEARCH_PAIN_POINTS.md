## 1. Design — why the current design isn't landing

**Core problem:** the graph is being drawn as a *general* graph-layout problem (nodes + edges, force/spring layout) instead of a *hierarchical containment* problem (modules contain submodules contain files). Codebases have a natural tree/DAG-of-containment structure; users expect to navigate that tree, not decode a hairball.

- **Match the mental model, not the data structure.** A repo's top-level modules (`sql-pool`, `sql-api-service`, …) are a *level* of the hierarchy, not just densely-connected nodes among thousands. Tools built specifically for this — CodeSee (auto-generated maps that "start broad and let you open or collapse folders as needed") and the archived-but-still-referenced Sourcetrail (graph + drill-down navigation used as the benchmark for "jump from symbol to symbol") — both default to a collapsed top level with explicit expand/drill-down, not one flat graph of everything ([repowise.dev comparison](https://repowise.dev/blog/comparisons/best-codebase-visualization-tools), [CodeSee via GitKraken learning center](https://repowise.dev/blog/comparisons/best-codebase-visualization-tools)).
- **Single-line/overlapping layout is a symptom of using the wrong layout algorithm for a hierarchical graph.** Pure force-directed layouts "highlight the underlying topology... but if the graph is too highly connected or unstructured, it will tend to produce a hairball" (Cytoscape.js layout guide, [blog.js.cytoscape.org](https://blog.js.cytoscape.org/2020/05/11/layouts/)). For DAG/tree-like structures — which module containment is — hierarchical layouts (dagre, ELK layered) "avoid overlap by construction" rather than needing iterative repulsion tuning. Recommendation for next design pass: treat the top level as a **layered/hierarchical layout** (dagre or ELK's layered algorithm), reserve force-directed layout (if at all) for *within* a single dense leaf cluster, not the whole graph.
- **Correction (see Section 0): this split already exists in code**, not just as a recommendation — `graphLayout.ts:139-177` (`layoutRanked`) runs dagre for grouped/ranked altitudes, `graphLayout.ts:102-129` runs ForceAtlas2 + a `noverlap` anti-overlap pass for the raw ones. The open question is narrower than "pick a layout engine": it's whether the existing dagre single-node-rank jitter (`graphLayout.ts:150-171`) and `noverlap`'s 250-iteration/margin-6 settings (`:59-67`) actually hold at `unified-store`'s real node/fan-out count, which the code comments verify only against a 7-node synthetic case.
- **Alternative worth evaluating, not adopting blind:** a treemap/city-metaphor view (CodeCharta) is a different paradigm — area-encoded, good for size/complexity at a glance, weaker for "what calls what" — likely a *complement* to a hierarchical graph, not a replacement ([codecharta.com](https://codecharta.com/)).

**For next agents:** design deliverable should specify (a) which layout engine per zoom level, (b) the containment levels to render (module → submodule → package/config → file, matching the user's own example), (c) a fallback for genuinely flat/dense leaf sets.

## 3. Optimization / making it fast

**Constraint from project rules:** no root cause should be proposed without profiling/timing/log evidence. The bullets below separate (a) what's empirically knowable from the user's description alone, (b) what generic causes are worth checking for tools of this shape, and (c) what data the next agent needs to collect before touching code.

- **What we know without more data:** the "loading forever, fixed by navigating away and back" pattern is a *symptom description*, not a diagnosis. It's consistent with several distinct root causes (stuck in-flight request never resolving, a fetch resolving but not triggering a re-render/cache update, a race between two competing fetches on rapid clicks, or an unhandled rejection silently swallowing the loading-state reset) — each requires a different fix, and each is distinguishable only by instrumentation (network tab timing, a request-ID log at fetch start/resolve, a console trace on component mount/unmount). **Action for next agent: capture this evidence before proposing a fix**, per this repo's debugging-process rule.
- **Layout algorithm choice affects perceived latency directly.** Dagre is explicitly positioned as "focus on speed over choosing the most optimal layout" — i.e., the right choice for interactive graphs where responsiveness matters more than marginal layout aesthetics; ELK is "more powerful but heavier," better for one-time high-quality static layout, not for real-time interaction ([reactflow.dev layouting overview](https://reactflow.dev/learn/layouting/layouting), [dtoyoda10 ELK/dagre comparison](https://dtoyoda10.medium.com/building-complex-graph-diagrams-with-react-flow-elk-js-and-dagre-js-8832f6a461c5)). If the current graph feels slow *and* dense, the layout engine itself is a candidate to measure, not just network latency.
- **Request lifecycle hygiene (generic best practice, applies regardless of root cause found):** cancel in-flight requests on unmount/navigation (`AbortController`) so a stale response from a previous tile can't land on top of new state; this is a standard fix for "stuck/stale" loading in SPA data-fetching and is worth checking for regardless of what the logs show, since its absence is a common contributor to exactly this class of bug.
- **Rendering cost at scale.** For genuinely large/dense graphs (the `unified-store` case), canvas/WebGL rendering with viewport culling (only render nodes in view) scales far better than one DOM/SVG node per graph node; this becomes relevant once drill-down + search are in place and the leaf-level node counts are known — a decision to make with real node-count data, not assumed thresholds.
- **Near-real-time framing:** true "real-time" (push updates) is likely unnecessary here — the ask is "fast and doesn't get stuck," which is a correctness/latency problem, not a live-sync problem. Recommend not scoping in websockets/subscriptions unless the user separately asks for live repo-change updates.

**For next agents:** before any optimization work, produce a timing/profile capture of (1) the stuck-tile scenario end-to-end, (2) layout-computation duration at current `unified-store` node count. Do not propose a fix without that data.

## 4. UI/UX — making the graph informative

- **Encode module type/role visually, consistently, with a legend.** Right now overlap makes even distinguishing nodes hard; once layout is fixed, users still need a way to tell "this is a service module" vs "this is a config" at a glance — consistent color/shape by category plus a persistent legend key, the same pattern used across the surveyed tools (CodeCharta uses visual encoding for metrics like complexity/churn; CodeSee differentiates module/service boundaries visually).
- **Progressive disclosure instead of one dense view.** Show a *collapsed* top level by default (the 6–7 modules the user named), expand on demand. This directly addresses "too much overlapping" — fewer nodes visible by default means less to overlap, and it matches how users already think about the codebase (they named the modules unprompted, meaning that's their existing mental map).
- **Minimap / "you are here" indicator** once drill-down exists, so users don't lose orientation navigating from a top-level module into a submodule and back — standard in code-map tools once nesting is introduced.
- **Tooltips/hover detail** (file count, last-changed, owning team if known) rather than requiring a click to learn what a node is — reduces exploratory clicking that currently triggers the stuck-loading bug.
- **Distinguish "empty because still loading" from "empty because there's nothing here."** Part of why the stuck-tile bug reads as broken rather than slow is the lack of any visible state difference between "fetching" and "silently failed" — an explicit loading skeleton + distinct empty-state + distinct error-state closes this gap and is a UX fix as much as a functional one (overlaps with Section 2).

## 5. Motion & animation design (this cycle's research)

Requested this cycle: research "beautiful, animation-based" graph designs and map findings back to the pain points already logged above, not restate them.

- **Animation here is not decoration — it's the fix for a named pain point.** Section 4 already flags that instantaneous re-layout on drill-down disorients users. This is a documented failure mode, not a guess: Tidwell's animated-transition pattern and Berkeley's radial-layout research both treat "state change without animation" as the actual defect — an instantaneous jump forces the user to relocate every node from scratch, while an eased transition lets the eye track continuity ([Designing Interfaces — Animated Transition](https://designinginterfaces.com/patterns/animated-transition/); [Berkeley — Animated Exploration of Graphs with Radial Layout](https://bailando.berkeley.edu/papers/infovis01.htm)). Directly actionable against the breadcrumb-stack drill-down `MONOREPO_HIERARCHY.md` §3 proposes: each ascend/descend should animate node position deltas, not swap layouts frame-to-frame.
- **Sequence node and edge removal together, not in two passes.** GraphDiaries' finding is specific and non-obvious: animating edges out first, then nodes, leaves users unable to tell whether a node was isolated or just had its edges hidden first ([GraphDiaries, aviz.fr](https://aviz.fr/~bbach/graphdiaries/Bach2013GraphDiaries.pdf)). Relevant to the existing dagre/noverlap pipeline (`graphLayout.ts`, per last cycle's read) — any future re-layout animation on altitude switch should treat a node-and-its-edges as one atomic transition unit, matching the D3 enter/update/exit convention of animating opacity/position to zero *before* removal rather than an abrupt cut ([D3 transitions — Observable](https://d3js.org/d3-transition); [Understanding animated graphs in D3.js](https://danielrotter.at/2020/06/12/understanding-animated-graphs-with-d3js.html)).
- **Timing budget: ~200–300ms, interruptible, never sequential-stacked.** NN/g's guidance is concrete enough to set as a constraint: too fast reads as a glitch, too slow reads as lag, and multiple rapid user actions must collapse into one animation rather than queuing — directly relevant to the "spins forever" bug in Section 3, since a queue of stacked re-layout animations would look identical to the hang users already report, and any fix needs to guard against introducing a lookalike failure mode ([NN/g — Executing UX Animations](https://www.nngroup.com/articles/animation-duration/)).
- **If the render substrate stays Canvas, node-count budgets constrain what "beautiful" animation is affordable.** Independent benchmarks converge on Canvas (Cytoscape.js-class rendering) losing smooth frame rates around 3,000–5,000 nodes, with SVG lower still (~2k) and WebGL (Sigma.js-class) usable to 100k+ ([PkgPulse 2026 comparison](https://www.pkgpulse.com/guides/cytoscape-vs-vis-network-vs-sigma-graph-visualization-2026); [Memgraph — fast/easy/popular, pick two](https://memgraph.com/blog/you-want-a-fast-easy-to-use-and-popular-graph-visualization-tool)). **Unverified this cycle:** what `AtlasCanvas.tsx` actually renders with (Canvas2D vs SVG vs WebGL) — last cycle's read didn't check this specifically, and re-confirming it is a prerequisite before promising smooth per-frame animation at `unified-store`'s real node count, not something to assume from the filename.
- **Force-directed re-heat technique, if force layout is ever animated live (not just dagre's static layered pass):** D3's `alphaTarget` pattern — nudge the simulation's temperature up gently on data change instead of restarting cold — is the standard fix for the jitter/fighting-for-position artifact that a naive "just re-run force layout" produces ([Stamen — Forcing Functions](https://stamen.com/forcing-functions-inside-d3-v4-forces-and-layout-transitions-f3e89ee02d12/)). Lower priority here since Section 1 already established dagre (not force) is the right call for the hierarchical/ranked altitudes; this only matters if a future leaf-level dense cluster keeps ForceAtlas2.
- **Precedent worth studying directly, not just citing:** Obsidian's native graph view ships exactly the "beautiful animated graph" users may be picturing — force-directed physics (center/repel/link forces, adjustable link distance) plus a scrubbable time-lapse animation, and its own writeups flag the same architectural ceiling this doc has already named: graph-as-view rather than graph-as-navigation-interface ([Obsidian — Graph view help](https://obsidian.md/help/plugins/graph); analysis via [Digital Biz Talk](https://digitalbiztalk.com/article/beyond-visualization-an-interactive-graph-view-for-obsidian)). Worth a hands-on look (open an Obsidian vault, toggle "Animate") before committing to a specific easing/force recipe — cheaper to copy a working reference than to derive motion parameters from first principles.
- **Net recommendation, scoped to not conflict with Sections 1–3:** treat animation as a per-interaction spec, not a global toggle — (a) altitude ascend/descend: eased position interpolation of persisting nodes + atomic fade of entering/exiting node+edge sets, ~250ms, cancel-and-replace (not queue) on rapid re-clicks; (b) loading state: an explicit animated skeleton (already flagged missing in Section 4) so "still fetching" is visually distinct from a frozen animation mid-transition, which would otherwise look identical to the stuck-tile bug. Confirming this is affordable at `unified-store`'s scale still requires the render-substrate check and node-count data Section 3 already calls for — this section adds *what* the animation should do, not a substitute for that missing profiling.
